\section{Introduction}
The goal of this project is to study object-oriented databases and compare two database management systems, ObjectDB and ObjectBox. Object-oriented databases are designed to store and manipulate objects directly, without needing to map application objects to relational tables. This project will present the fundamental concepts of object-oriented database technology and examine how they are implemented in ObjectDB and ObjectBox. A common application will be developed using both systems to perform a set of representative queries and updates. The performance of these operations will then be evaluated on datasets of different sizes to analyze the scalability of each system. Finally, the results will be compared with those obtained using a traditional relational database management system, in order to see the advantages and limitations of object-oriented databases, and determine if it is the technology of choice for the application.

\section{Foundations of Object-Oriented Databases}

\subsection{Origins and motivation}

A lot of applications are built with object-oriented languages while storing their data in relational databases. The two models were designed around different principles, and the difficulties created by combining them are known as the \emph{object-relational impedance mismatch}.

An object has its own identity, separate from the values it holds. Two objects containing exactly the same data are still two different objects, and an object remains the same object even if every one of its fields is modified. A row in a relational table works differently because it is identified by its primary key, which is part of the data. If that key is modified, the row becomes a different row, and two rows holding the same values cannot be told apart.

Objects also point directly at one another. When an object holds a collection of other objects, accessing them only requires following a pointer.
The relational model works only with values that happen to match. The link has to be stored as a foreign key, and rebuilt every time it is needed by joining two tables. What is a single step in the application becomes a whole operation on sets in the database.

Three other features of object oriented principles have no equivalent in the relational model. Inheritance has to be flattened onto tables, and there are several ways to do it, with each one trading storage space for query speed.
Collections have to be moved into separate tables because a column can only hold one single value.
Encapsulation also disappears since a table shows all of its columns to anyone allowed to read it.

The result is that the application has to translate between the two models every time it reads or writes data. This translation is either written by hand or left to an object-relational mapping framework (ORM). Either way, it forms a layer that belongs neither to the application nor to the database, it has to be kept in step with the schema, and it brings problems of its own, such as loading far more data than was asked for, or running one query for every element of a collection.

Object-oriented databases take a different approach. Rather than translating objects into another model, they store them as they are, which removes the middle layer entirely.

\subsection{Fundamental Principles of Object-Oriented Database Management Systems}
\label{subsec:principles}

Object-oriented databases are built on a small number of ideas that together
allow objects to be stored without being transformed. This section presents them
one by one.

\paragraph{Object identity:} Every object that is stored receives an \emph{object
identifier} (OID). It is assigned by the database itself, it is unique and it
never changes during the life of the object. Since it is independent of the
values the object holds, two objects with the same content remain distinct, and
an object can have all of its fields modified while still being recognised as the
same object. This is what a primary key cannot provide.

\paragraph{Complex objects:} An object is allowed to be \emph{complex}, which
means it is not restricted to a single value for each of its attributes. An
attribute can hold another object, or a list, a set or a map of objects, and
those objects can in turn contain others. The structure that the application
works with is therefore stored as it is, without being split across several
tables and reassembled later.

\paragraph{Inheritance:} Classes can be organised in a hierarchy, and the
database is aware of it. A class inherits the attributes of its parent, and a
query written for a parent class also returns the instances of its subclasses.
The mapping strategies that the relational model requires for inheritance are not
needed, because the hierarchy is part of the stored schema rather than something
simulated on top of it.

\paragraph{References:} Relationships between objects are stored as
\emph{references}. An object holds a reference to another object, and following
that reference is a direct operation that does not depend on the size of the
database. Relationships can also be declared in both directions, in which case
the database keeps the two sides consistent when one of them is modified.

\paragraph{Persistence by reachability:} Saving an object saves everything it can
reach. When an object is made persistent, the objects it references become
persistent as well, and so on recursively. The application therefore stores a
structure in one operation instead of saving each part in the right order.

\paragraph{Navigation and queries:} Data can be accessed in two different
ways. \emph{Navigation} starts from one object and follows its references, which
suits operations that explore a known part of the structure. \emph{Declarative
queries} describe a condition and let the database find the matching objects,
which is suited for operations that search the whole database. Relational databases offer
only the second, while object-oriented systems offer both.

\paragraph{Transparent persistence:} An object read from the database is an
ordinary object of the language, meaning that it is ready to be used directly and it is not a result that
has to be converted first. Writing works the same way since modifying an object
inside a transaction is enough for the change to be stored. The translation layer
described in the previous section therefore disappears.

\subsection{Standards and norms}

Object-oriented databases got their definition in 1989, from a paper known as the \emph{Object-Oriented Database System Manifesto}\cite{manifesto}.
The authors listed thirteen features that a system must have to deserve the name.
Eight of them come from object orientation itself, namely complex objects, object
identity, encapsulation, types and classes, inheritance, overriding, extensibility
and computational completeness. 
The other five are what any database is expected to do, like storing data persistently, managing secondary storage, handling
concurrent access, recovering after a failure and answering ad hoc queries.

A group of vendors then tried to agree on a common standard. 
They formed the Object Data Management Group in 1991 and published a specification with an object model, 
a definition language (ODL), a query language close to SQL (OQL) and bindings for C++, Smalltalk and Java. 
The last version, ODMG 3.0, came out in 2000\cite{odmg}. A year later the group gave its Java binding to the Java
Community Process, where it became JDO, and then shut down. JDO was eventually succeeded by the Java Persistence API (JPA).

JPA was built for mapping objects onto relational tables, and it is normally used with a framework like Hibernate. 
But it only describes how the application talks to the database, not how the data is stored, so a real object database can
implement it too. 
ObjectDB does exactly that, which means that seeing JPA in the code does not imply there is a relational database underneath. 
What matters most is that today no single standard is followed by everyone. ObjectDB uses JPA, while ObjectBox has its own API 
and follows no standard at all.

\paragraph{Cost of following a relationship:} The cost of a join increases with the
number of rows involved, and an operation crossing several tables multiplies that
cost. But with object-oriented databases, you only need to follow a reference to reach a known object, whatever the size of
the database. So the deeper the structure being traversed, the larger the difference should be.

\paragraph{Expressing a query:} The relational model only offers declarative
queries but in a language that is standardised and supported by many tools.
Object-oriented systems also offer navigation, but their query languages differ from one product to another, so
code written for one cannot be reused with another.

\paragraph{Schema and evolution:} A relational schema is declared explicitly and
modified with well-established tools. In an object-oriented database it is
derived from the classes themselves, which then removes a source of duplication, but
changing those classes once data exists is handled differently by each product.

\paragraph{Maturity of the ecosystem:} Relational systems are backed by
decades of tooling and research. Object-oriented systems are less mature since they have been around for a shorter time, 
have smaller communities, less documentation and little external tool support. 
This is not really relevant to the technical qualities of either model, but it is a point of consideration when making a practical choice.

\section{Overview of the DBMS Studied}

\subsection{ObjectDB: Object DBMS for Java / JPA}

ObjectDB is a commercial object database written in Java and shipped as
a single JAR file\cite{objectdb_manual}. It stores Java objects as they are, and
you work with it through the standard Java Persistence API (JPA), or through Java
Data Objects (JDO) in older versions. As said in the previous chapter, using JPA
does not mean there is a relational engine underneath, because JPA only describes
how the application talks to the database.

There are two ways to run it. In \emph{embedded} mode the database lives inside
the application's own JVM and locks the database file for that one process. In
\emph{client-server} mode a separate server process, a Docker container for
example, owns the file and clients reach it over TCP/IP, so several processes can
share the same database. For our use case we use the embedded mode because it is
faster and it compares fairly with ObjectBox.

\paragraph{Declaring persistent classes:} You mark classes with the usual JPA
annotations. A class with \texttt{@Entity} becomes a stored object with its own
identity, while a class with \texttt{@Embeddable} is stored inside its owner and
does not exist on its own. Collections and maps are just Java fields, which is how
you get the complex objects described in Section~\ref{subsec:principles}.

\begin{lstlisting}[language=Java]
@Entity
public class Player {
    @Id private String playername;
    private String passwordHash;
    @OneToMany(cascade = CascadeType.ALL) private List<Team> teams;
}
\end{lstlisting}

\paragraph{Object identity:} Every stored object gets an identifier from ObjectDB
itself, so you do not have to declare a primary key. If you mark a field with
\texttt{@Id}, its value becomes the key and cannot be changed afterwards. With
\texttt{@GeneratedValue} the database picks the key for you, by default a
sequential 64-bit number starting at one, and it never reuses the keys of deleted
objects\cite{objectdb_manual}. To find an object you need its class and its key.

\paragraph{Storage:} A database is one file, usually ending in \texttt{.odb}, and
it can grow to hundreds of gigabytes. Objects of the same class are written in
primary key order, so the key you choose also decides which objects end up close
to each other on disk\cite{objectdb_manual}. Queries are written in JPQL, the
query language that comes with JPA, or built in code with the Criteria API.

\paragraph{Indexing:} You declare indexes on fields with \texttt{@Index}, and
they can cover one field, several fields, or enforce uniqueness. They also work
on elements of collections, on keys and values of maps, and on fields inside
embedded objects. Without the right index a query has to go through every object
of the class, so indexes are what make queries on a large database usable. They
also cost space and slow down writes, and an index added to a class that already
holds objects does not work until everything already stored has been indexed.

\paragraph{Caching:} ObjectDB caches at three levels. Each \texttt{EntityManager}
keeps the objects it is managing, so asking for the same object twice gives you
the same instance back. Above that sits an optional shared cache owned by the
\texttt{EntityManagerFactory}, which helps when the application creates a lot of
short-lived entity managers. It is turned off by default and you have to give it
a size in the configuration file\cite{objectdb_manual}. Finally the database side
caches file pages, compiled queries and query results, and those are configured
per database rather than per client.

\paragraph{Strengths and limitations:} Its main strength is that it follows a
standard. Since the API is JPA, the same code can be moved to a relational
database with Hibernate without much work, and what you learn is not tied to one
product. On the other hand, it is a commercial product, and its free edition
refuses to store more than one million entity objects in a single database file
or to declare more than ten persistable classes\cite{objectdb_license}. These are
limits enforced by the library itself, so going beyond them requires buying a
licence whatever hardware the database runs on. It also only exists for Java, and
its community and documentation are small in comparison to the relational systems
it competes with.

\section{Use Cases and Domain Modeling}

\subsection{Description of the application domain}
The application domain selected for this benchmark is inspired by a multiplayer online role-playing game (RPG) system modeled after the Pokemon franchise. In this context, persistent storage must support two distinct categories of data:
\begin{enumerate}
    \item \textbf{Static reference data}: immutable entities representing Pokemon (with a name, a type, a speed, ...) and item definitions (name of the item and its description).
    \item \textbf{Dynamic player state}: mutable user data tracking account credentials, active team selections, customized teams and inventory management.
\end{enumerate}

This domain serves as an ideal case study for comparing Object-Oriented Database Management Systems (OODBMS) with traditional Relational Database Management Systems (RDBMS). Player profiles exhibit a high degree of structural complexity, including nested collections of variable length (such as lists of team members or associations between inventory items and their quantities), object composition, and complex references between entities.

\subsection{Conceptual schema and data models}

To compare the relational approach with implementations in object-oriented databases, the RPG domain model is represented using three distinct data modeling paradigms: a conceptual domain model, a normalized relational model, and object-oriented data models.

\subsubsection{Conceptual Domain Model}
Conceptually, the domain models player management and in-game inventory through relationships between entities and complex data structures:
\begin{itemize}
	\item \textbf{Player}: Represents a user account identified by a unique \texttt{playername}, storing an authentication hash (\texttt{passwordHash}), an active team reference (\texttt{currentTeam}), a collection of saved teams (\texttt{teams}), and an inventory mapping items to quantities.
	\item \textbf{Team}: Defines a named user team (\texttt{name}) containing an ordered list of 1 to 6 Pokemon members.
	\item \textbf{Pokemon}: Represents game creatures defined by base stats (\texttt{hp}, \texttt{attack}, \texttt{defense}, \texttt{spAtk}, \texttt{spDef}, \texttt{speed}), typing (\texttt{type1}, \texttt{type2}), generation, and legendary status.
	\item \textbf{Item}: Represents consumable or collectible items with a unique \texttt{id}, \texttt{name}, and \texttt{description}.
	\end{itemize}
		
		\subsubsection{Relational Data Model (PostgreSQL Baseline)}
		In the relational model, object structures with nested collections and references must be decomposed into Third Normal Form (3NF) relational tables linked by foreign key constraints:
		\begin{itemize}
			\item \texttt{pokemons} \& \texttt{items}: Catalog tables holding static reference data indexed by primary keys (\texttt{id} and \texttt{item\_id}).
			\item \texttt{players}: Stores user account details and holds a foreign key \texttt{(playername, current\_team)} referencing the player's active team in the \texttt{teams} table.
			\item \texttt{teams}: Maps each team to its owner via \texttt{playername}, using a composite primary key \texttt{(playername, name)}.
			\item \texttt{team\_members}: Junction table modeling the list of Pokemon within a team, storing \texttt{(playername, team\_name, pokemon\_id, slot\_position)}.
			\item \texttt{item\_player}: Junction table representing player inventories, mapping \texttt{playername} and \texttt{item\_id} alongside an \texttt{amount} attribute.
		\end{itemize}
		
		\subsubsection{Object-Oriented Data Model (ObjectDB / JPA)}
		ObjectDB leverages standard Java Persistence API (JPA) annotations to persist an object graph directly, while preserving object integrity without resorting to relational normalization:
		\begin{itemize}
			\item \textbf{Entities vs. Embeddables}: \texttt{Player} and \texttt{Team} are declared as standalone persistent entities (\texttt{@Entity}). \texttt{Pokemon} and \texttt{Item} are lightweight value objects decorated with \texttt{@Embeddable}.
			\item \textbf{Direct Collection \& Map Storage}: Player inventories are mapped directly as a key-value map using \texttt{@ElementCollection Map<Item, Integer>}. Team membership lists (\texttt{List}) are embedded directly within the parent \texttt{Team} instance.
			\item \textbf{Object Relationships}: Relationships are defined using cascade options (\texttt{CascadeType.ALL}) associated with \texttt{@OneToMany} and \texttt{@OneToOne}, which enables full persistence by reachability when saving a \texttt{Player} object.
		\end{itemize}
		
		\subsubsection{Embedded Object Data Model (ObjectBox)}
		ObjectBox implements a standalone object-oriented storage system, optimized for low-latency embedded execution:
		\begin{itemize}
			\item \textbf{Relations}: Uses \texttt{ToOne} and \texttt{ToMany} smart relation wrappers to handle directed graph edges.
			\item \textbf{Map Decomposition}: Because ObjectBox natively supports entity-to-entity relations rather than arbitrary key-value Java maps, inventories are explicitly modeled using an intermediate \texttt{InventoryEntry} entity containing a \texttt{ToOne} relation and an integer quantity field.
		\end{itemize}

\subsection{Software architecture}
The system architecture is engineered to provide a strictly fair and reproducible evaluation across the benchmarked database systems. It decouples dataset generation, object model management, and database execution through modular design patterns.

\subsubsection{Architectural Overview}
The software adopts a multi-level architecture, structured around three key layers:
\begin{enumerate}
	\item \textbf{Data Generation Tier}: Reads static CSV files (\texttt{pokemons.csv}, \texttt{items.csv}) and deterministically constructs player object graphs serialized into JSON files (\texttt{DatasetGenerator}).
	\item \textbf{DAO Layer (Data Access Object)}: Encapsulates database-specific persistence, retrieval, and schema management logic behind a common interface (\texttt{BenchmarkDao}).
	\item \textbf{Benchmarking Engine}: Orchestrates dataset loading, database cleanup, transaction boundary controls, warm-up iterations, and the measurement of execution time (\texttt{BenchmarkRunner}).
\end{enumerate}

\subsubsection{Design Patterns and Implementation Details}

\begin{itemize}
	\item \textbf{Data Access Object (DAO) Pattern}: The \texttt{BenchmarkDao} interface exposes four primary operations: \texttt{init()}, \texttt{clearDatabase()}, \texttt{insertPlayers(List)}, and \texttt{close()}. This abstraction guarantees that the benchmarking execution loop remains entirely decoupled from concrete persistence drivers.
	\item \textbf{Relational Batch Optimizations}: The \texttt{PostgresDao} implementation utilizes JDBC prepared statement batching along with the \texttt{reRewriteBatchedInserts=true} connection property to optimize relational multi-row insertions.
	\item \textbf{Object-Oriented Transaction Management}: \texttt{ObjectDbDao} manages persistence through an active JPA \texttt{EntityManager} transaction, utilizing cascade persistence to automatically persist complete player reachability graphs. \texttt{ObjectBoxDao} executes atomic batch put operations inside native \texttt{store.runInTx()} blocks.
\end{itemize}

\subsection{Dataset generation}
To evaluate scalability under realistic database workloads while adhering to rigorous benchmarking practices, a hybrid data generation strategy was implemented.

\subsubsection{Authentic Reference Datasets}
Rather than generating purely synthetic game entities, the static reference data was populated using real-world datasets extracted from an online database library (\emph{Kaggle}):
\begin{itemize}
    \item \texttt{pokemons.csv}\cite{kaggle_pokemon}: Contains 800 Pokemon with complete attributes (\texttt{HP}, \texttt{Attack}, \texttt{Defense}, \texttt{Sp. Atk}, \texttt{Sp. Def}, \texttt{Speed}, \texttt{Generation}, \texttt{Legendary}).
    \item \texttt{items.csv}\cite{kaggle_item}: Contains 920 game items with names and descriptions.
\end{itemize}

\subsubsection{Deterministic Workload Generator}
To simulate scalable player bases ($1\text{K}$, $10\text{K}$, $100\text{K}$, and $1\text{M}$ objects), a Java generator (\texttt{DatasetGenerator.java}) was constructed using a fixed seed (\texttt{SEED = 12345L}). This guarantees 100\% deterministic reproducibility across benchmarking runs.

For each generated player profile:
\begin{enumerate}
    \item A unique identifier \texttt{Player\_i} is assigned as the player name (where $i \in \{1, \dots, N\}$ represents the $i$-th generated player), and \texttt{password\_hash} is populated using a deterministic hash derived from the player's name.
    \item A random subset of $1$ to $10$ distinct Pokemon is assigned from the reference list without replacement.
    \item $1$ to $10$ custom teams are constructed, each containing $1$ to $6$ member slots populated from the player's owned Pokemon.
    \item An inventory is generated containing $1$ to $10$ distinct items with randomized quantities ranging from $1$ to $10$.
\end{enumerate}

Overall, both object-oriented systems outperform PostgreSQL by approximately an order of magnitude when it comes to the large-scale persistence of graphs, and by a factor of 2 to 10 for individual read and update operations under steady-state conditions, with up to 100 000 players.

\subsection{Scalability analysis}

\subsubsection{Insertion rate and scaling of complex objects}
Insertion latency highlights the fundamental architectural divergence between relational decomposition and object graph persistence:

\begin{itemize}
	\item \textbf{PostgreSQL:} Insertion time grows almost linearly from 505.23 ms at 1K to 674 640.10 ms at 1M ($1.33 \approx 1$ from $1\text{K}$ to 1M). Throughput peaks at $\approx 1\,980\text{ players/s}$ at $1\text{K}$ (and $\approx 1\,714\text{ players/s}$ at $10\text{K}$) and declines to $\approx 1\,482\text{ players/s}$ at $1\text{M}$. Even with JDBC batch rewriting enabled (\texttt{reWrite\-BatchedInserts=true}), persisting a single \texttt{Player} object graph requires flattening nested collections into normalized rows across four tables (\texttt{players}, \texttt{teams}, \texttt{team\_members}, and \texttt{item\_player}), validating foreign key constraints, to write records to the transaction log via a TCP socket, etc.
	
	\item \textbf{ObjectDB:} ObjectDB achieves the highest ingestion throughput across all completed scales, running $10.75\times$ faster than PostgreSQL at $1\text{K}$ ($46.98\text{ ms}$), $12.08\times$ faster at $10\text{K}$ ($482.75\text{ ms}$, scaling linearly by $10.28\times$), and $16.77\times$ faster at $100\text{K}$ ($3\,643.15\text{ ms}$, roughly $27\,450\text{ players/s}$). Because \texttt{Pokemon} and \texttt{Item} are stored as \texttt{@Embeddable} value objects and \texttt{Team} relationships use \texttt{CascadeType.ALL}, ObjectDB traverses the reachability graph in memory and writes contiguous object pages directly into a single \texttt{.odb} file without join-table fan-out.
	
	\item \textbf{ObjectBox:} ObjectBox completes insertions $5.07\times$ to $6.00\times$ faster than PostgreSQL ($95.14\text{ ms}$ at $1\text{K}$, $1\,151.15\text{ ms}$ at $10\text{K}$, and $10\,183.68\text{ ms}$ at $100\text{K}$), but remains $2.03\times$ to $2.80\times$ slower than ObjectDB. Two factors explain this gap. First, ObjectBox lacks native embedded maps, requiring player inventories to be decomposed into explicit \texttt{InventoryEntry} entities linked via \texttt{ToOne} and \texttt{ToMany} relations inside \texttt{store.runInTx()}. Second, the raw traces reveal consistent post-warmup latency on Run~2 ($225.52\text{ ms}$ at $1\text{K}$, $2\,869.86\text{ ms}$ at $10\text{K}$, and $24\,028.50\text{ ms}$ at $100\text{K}$) caused by memory-mapped store expansion; once stabilized in Runs~3--6, ObjectBox averages $62.54\text{ ms}$, $721.47\text{ ms}$, and $6\,722.48\text{ ms}$, respectively.
\end{itemize}

\subsubsection{Point retrieval (GET) and graph traversal latency}
Point retrieval measures the cost of locating a single \texttt{Player} by identifier and reconstructing its complete object graph (owned teams, team rosters, and inventory items):

\begin{itemize}
	\item \textbf{PostgreSQL:} Retrieval latency exhibits logarithmic-to-constant scaling across three orders of magnitude, rising by only $19.2\%$ ($1.19\times$) from $1.46\text{ ms}$ at $1\text{K}$ to $1.74\text{ ms}$ at $1\text{M}$. Whileforeign key indexes keep lookup times tightly bounded even at one million players, absolute latency remains higher than in both OODBMSs. Reconstructing a single player profile requires traversing normalized junction tables (\texttt{teams}, \texttt{team\_members}, \texttt{item\_player}), incurring TCP/IP round-trip communication overhead.
	
	\item \textbf{ObjectDB:} ObjectDB retrieves full player graphs $2.06\times$ to $5.24\times$ faster than PostgreSQL, recording $0.60\text{ ms}$ at $1\text{K}$, $0.29\text{ ms}$ at $10\text{K}$, and $0.84\text{ ms}$ at $100\text{K}$. Embedded execution eliminates network serialization, while direct object references allow the \texttt{EntityManager} to materialize owned \texttt{Team} entities and embedded \texttt{Pokemon} and \texttt{Item} collections without relational joins. The initial drop from $0.60\text{ ms}$ to $0.29\text{ ms}$ reflects JVM Just-In-Time (JIT) compilation and page-cache warming, whereas the increase to $0.84\text{ ms}$ at $100\text{K}$ (where total stored \texttt{Player} and \texttt{Team} entities approach the one-million mark) stems from larger index traversals, page-cache misses, and Java heap allocation overhead.
	
	\item \textbf{ObjectBox:} ObjectBox delivers the lowest retrieval latency at every tested scale, averaging $0.21\text{ ms}$ at $1\text{K}$, $0.12\text{ ms}$ at $10\text{K}$, and $0.21\text{ ms}$ at $100\text{K}$. This makes it $6.95\times$ to $12.67\times$ faster than PostgreSQL and $2.42\times$ to $4.00\times$ faster than ObjectDB. Crucially, its latency shows virtually zero degradation between $1\text{K}$ and $100\text{K}$ players. Because ObjectBox stores entities as FlatBuffers inside memory-mapped files (\texttt{mmap}) and executes queries in a native C++ core, reading a \texttt{Player} and traversing its \texttt{ToOne}/\texttt{ToMany} links avoids both network IPC and heavy intermediate object parsing.
\end{itemize}


\subsubsection{Entity updates and transactional persistence}
Transactional updates evaluate the overhead of mutating an existing persistent player state and committing the change to durable storage:

\begin{itemize}
	\item \textbf{PostgreSQL:} Update latency stays nearly flat across all dataset sizes, fluctuating within a narrow band between $1.74\text{ ms}$  for $1\text{K}$ and $2.11\text{ ms}$ for $10\text{K}$, and stabilizing at $1.81\text{ ms}$ for $100\text{K}$ and $1.83\text{ ms}$ for $1\text{M}$. Execution time is primarily determined by fixed costs per transaction: network round-trips between the client and the server, execution of SQL statements, etc.
	
	\item \textbf{ObjectDB:} ObjectDB sustains an almost constant update latency of $0.33\text{ ms}$ at $1\text{K}$, $0.23\text{ ms}$ at $10\text{K}$, and $0.31\text{ ms}$ at $100\text{K}$, outperforming PostgreSQL by $5.27\times$ to $9.17\times$. Through JPA transparent persistence and automatic dirty tracking within the active \texttt{EntityManager}, mutations applied to a managed \texttt{Player} instance are detected in memory and flushed directly to the corresponding object pages in the \texttt{.odb} file upon transaction commit, bypassing query translation.
	
	\item \textbf{ObjectBox:} ObjectBox achieves comparable update performance, recording $0.27\text{ ms}$ at $1\text{K}$, $0.29\text{ ms}$ at $10\text{K}$, and $0.41\text{ ms}$ at $100\text{K}$ ($4.41\times$ to $7.28\times$ faster than PostgreSQL). Unlike its flat read profile, ObjectBox's latency increase by $+51.9\%$ between $1\text{K}$ and $100\text{K}$ ($0.27\text{ ms}$ to $0.41\text{ ms}$), becoming slightly slower ($1.26\times$ to $1.32\times$) than ObjectDB at $10\text{K}$ and $100\text{K}$. Updating a player graph in ObjectBox requires re-serializing modified FlatBuffer records and synchronizing intermediate relation entities (such as \texttt{InventoryEntry} and \texttt{Team} links) inside \texttt{store.runInTx()}.
\end{itemize}

\subsection{Critical analysis by DBMS}

\subsubsection{PostgreSQL}
PostgreSQL illustrates the classic trade-offs inherent in relational database management systems based on a client-server architecture. Its primary limitation in this domain is the \emph{object-relational impedance mismatch}: decomposing hierarchical player profiles across four normalized tables increases processing time ($61.10\text{ s}$ vs.\ $3.64\text{ s}$ on ObjectDB at $100\text{K}$), even with JDBC batching optimizations enabled. Similarly, point reads and updates incur a baseline latency floor of $\approx 1.5$--$2.1\text{ ms}$ due to relational join reconstruction and client-server TCP/IP round-trips.

However, PostgreSQL is the \emph{only} evaluated system capable of completing the full $1\,000\,000$-player benchmark without failure or restriction. PostgreSQL proves to be the most resilient choice when dataset volume exceeds single-node embedded limits or requires shared multi-process access.

\subsubsection{ObjectDB}
ObjectDB aligns closest with the conceptual domain model and eliminates the impedance mismatch almost entirely. Using standard JPA annotations (\texttt{@Entity}, \texttt{@Embeddable}, \texttt{@ElementCollection}, and \texttt{Cascade\-Type.ALL}), complex collections such as player inventories (\texttt{Map<Item, Integer>}) and team rosters are persisted natively via reachability. This direct mapping between objects and pages enables the highest insertion rates in the benchmark for bulk data insertion. (up to $16.77\times$ faster than PostgreSQL at $100\text{K}$) as well as rapid, constant-time transactional updates ($0.23$--$0.33\text{ ms}$). Furthermore, using JPA preserves portability to relational storage systems should architectural requirements evolve.

However, ObjectDB has a notable drawback. Its commercial licensing model limits the free edition to 1 million persistent entity instances and 10 persistable classes. Given that each \texttt{Player} entity can have up to 10 distinct \texttt{Team} entities, scaling to support 1 million players results in approximately 6.5 million entity objects hitting the strict limit imposed by the license.

\subsubsection{ObjectBox}
ObjectBox is built for ultra-low-latency embedded persistence, and the empirical results confirm its strength on read-heavy workloads. Powered by a native C++ storage engine, memory-mapped file I/O, and zero-copy FlatBuffers serialization, it achieves sub-millisecond point retrievals ($0.12$--$0.21\text{ ms}$) that remain invariant from $1\text{K}$ to $100\text{K}$ players, outperforming PostgreSQL by up to $12.67\times$ and ObjectDB by up to $4.00\times$.

Its limitations stem from its data model expressiveness, proprietary API, and memory-mapped architecture at extreme scale. Because ObjectBox does not natively support embedded key-value maps, inventories must be manually normalized into auxiliary \texttt{InventoryEntry} entities, linked via \texttt{ToOne} and \texttt{ToMany}relationships, that makes bulk inserts $2.03\times$ to $2.80\times$ slower than ObjectDB. In addition, the system exhibits visible latency spikes when expanding its memory-mapped store (Run~2) and reaches native memory-mapped storage and reset limits at the $1\text{M}$-player scale, where tens of millions of interconnected entities must be managed within a single embedded store.
